# Tick 資料容量與回測儲存規劃

日期：2026/09/24。這是可用於配置硬碟的情境估算，不是已量測的全市場總量。
範圍為 2026/03/01～2026/09/24、上市與上櫃普通股，參考日曆共 144 個交易日。
目前股票清單 1,978 檔；ETF、興櫃及尚未補齊的下市／轉板歷史不在本估算範圍內。
不包含委託簿深度、逐筆委託、衍生商品或持續增加的未來日期。

## 結論

- 正式 tick 主檔：以 **10 GiB** 作基準配置，保守預留 **25 GiB**。
- 主檔、回測快取、衍生 K 線、轉換暫存及一份備份合計：**55～85 GiB**。
- 建議整個專案抓 **100 GiB 可用空間**的預算，約十進位 107 GB；備份放另一個儲存位置。
- 長期主檔使用 **Parquet + ZSTD**；頻繁回測使用有限大小、可重新建立的 **DataFrame pkl 快取**。

目前下載器仍以 JSON.gz 寫入，這份規劃沒有修改正式儲存流程。

## 估算根據

9/23 的八檔實際 API 樣本共 57,162 筆；沒有複製或合成資料來放大樣本。
相同資料、完整八個原始欄位及 metadata，格式補測結果如下。

| 格式 | 樣本 bytes/tick | 整批讀取還原 DataFrame 中位數 |
| --- | ---: | ---: |
| JSON.gz | 8.55 | 57.54 ms |
| DataFrame pkl.gz | 8.85 | 2.75 ms |
| DataFrame pkl | 64.18 | 1.09 ms |
| Parquet + ZSTD level 3 | 11.19 | 6.92 ms |

以上為 31 輪、兩輪暖機後的本機 OS cache 測試，非外接硬碟冷讀吞吐量。
所有格式讀回均逐值比對原始 DataFrame，整數奈秒時間戳保持一致。
Parquet 測試為每股票一檔、保留 pandas dtype 及 metadata；小檔案的固定成本也包含在內。

另由證交所 9/23 公開日成交資料，依目前普通股清單過濾，1,081 個匹配代碼合計
3,606,582 筆交易。官方大盤股票分類總計為 3,607,695 筆。此統計與 Shioaji
歷史 tick 的範圍／紀錄方式不同，**不能直接視為 API 應回傳的列數**。
五檔上市樣本的 API 列數／官方交易筆數約在 0.088～0.421 之間，足以說明不能
用單一股票比例換算整個市場。此次無法取得櫃買公開端點的完整回應，未虛構其筆數。

用上述百萬級市場活動作尺度參考，規劃三種**假設**：全市場每天 100 萬、300 萬、
800 萬筆 API tick。300 萬作偏保守基準；800 萬是假設整個期間每天皆高量的壓力情境。
這些不是抽樣統計信賴區間，也不是硬性上限。先前五檔外推的約 9 MiB/day 不再作
硬碟容量規劃基礎。

容量採 Parquet 實測 11.19 bytes/tick 向上配置為 **16 bytes/tick**，涵蓋其他股票的
壓縮差異與檔案組織差異，再加 **20%** 管理與波動餘裕。

```text
期間主檔容量 GiB
  = 每日假設 tick 數 × 144 日 × 16 bytes × 1.20 ÷ 1024³
```

| 情境 | 全市場每日 tick 假設 | 每日壓縮量，未加20% | 期間筆數 | 期間容量，已加20% |
| --- | ---: | ---: | ---: | ---: |
| 低量 | 100 萬 | 15.3 MiB | 1.44 億 | 2.6 GiB |
| 偏保守基準 | 300 萬 | 45.8 MiB | 4.32 億 | 7.7 GiB |
| 高量壓力 | 800 萬 | 122.1 MiB | 11.52 億 | 20.6 GiB |

因此配置上使用 10 GiB 基準／25 GiB 保守預留，比報一個小樣本外推的單點數字更實用。
若還保留一份完整 JSON.gz 原檔，應另加空間；下方預算假設校驗後只把 Parquet 留作
唯一正式格式，JSON.gz 是下載／轉換階段的暫存，沒有永久雙份保存。

## 適合頻繁回測的組織方式

### 1. 正式原始資料：Parquet + ZSTD

```text
ticks/year=2026/month=03/symbol=2330/part-000.parquet
ticks/year=2026/month=04/symbol=2330/part-000.parquet
```

- 以股票、月份分區；這個期間大約 1,978 × 7 = 13,846 個股票月單位。
- 下載仍按股票日保存進度，月資料完整後才合併，避免永久留下約 28 萬個小檔案。
- 合併後依交易日、原始順序存放，盡量讓 row group 對齊交易日，方便跳過無關日期。
- 只讀策略所需欄位，例如 `ts, close, volume`。Parquet 支援欄位投影及利用 row-group
  統計過濾；pkl 需先還原整個保存物件。
- 保留 `ts` 的 int64 奈秒值、完整價格精度及重複時間戳的不同成交，不為節省容量
  任意轉 float32 或去重。其他欄位改型別需先檢查範圍及資料一致性。
- 保留來源、代碼、日期、schema 版本、SHA-256 及列數清單；日期／股票範圍直接由索引定位。

這次小樣本中 Parquet 的全欄讀取比 pkl.gz 慢，也比 pkl.gz 大；選它作正式檔是為了
長期欄位式查詢與分區資料管理，不宣稱它在所有操作都較快或較小。

### 2. 常用回測資料：有限大小的 DataFrame pkl 快取

```text
cache/<source_hash>/<feature_version>/<symbol_and_window>.pkl
```

- 只快取最近反覆使用的股票與期間；以 **20 GiB** 作可調整的 LRU 容量上限。
- 熱資料用未壓縮 pkl，實測還原成本最低；不常用時可以移除，從 Parquet 重建。
- 快取鍵包含原始檔 hash、轉換／特徵版本及參數，避免使用陳舊計算结果。
- 同一次多組參數回測，在記憶體允許時共用已載入資料，不為每個參數組合重新解壓。
- 不把全期間資料一次載入 RAM。基準情境 4.32 億筆 × 8 欄 × 8 bytes，單是原始
  數值陣列就約 **25.7 GiB**，還不含分組、排序、指標計算的額外工作空間。

### 3. 衍生資料：K 線與常用特徵另外保存

把 1 分／5 分 OHLCV、VWAP 等常用結果按明確定義預先建立，使用同樣的日期／股票
分區與來源版本。K 線策略優先讀取這些資料；需要成交順序或 tick 層級模擬時才讀原始 tick。
此類資料先配置 **5 GiB**，大量特徵矩陣或多版本實驗需另設上限，不視為永久無上限保存。

## 空間配置

| 用途 | 容量預算 |
| --- | ---: |
| 正式 Parquet 主檔 | 10～25 GiB |
| 一份備份，另存不同位置 | 10～25 GiB |
| 常用未壓縮 pkl 快取，上限 | 20 GiB |
| K 線與有限版本的指標 | 5 GiB |
| 合併、轉換暫存空間 | 10 GiB |
| 合計 | 55～85 GiB |

抓整體 **100 GiB** 的預算即可容納上述設計；不是說原始 tick 本身就需要 100 GiB。
頻繁回測的工作檔與快取優先放 SSD。此預算不包含無上限的回測結果、未來新增月份或
任意複製整份資料的實驗。
